# بيئة API الداخلية — منصة متابعة المحتوى المحلي

## عزل كامل عن الموقع الحالي

- هذا العمل محفوظ في الفرع `internal-sqlserver-api-work` المبني على فرع التحويل الداخلي.
- لا توجد أي تغييرات على `main` أو إعدادات GitHub Pages أو قاعدة Supabase الحالية.
- لا تدمج هذا الفرع ولا تنشره على GitHub Pages؛ النشر المقصود لاحقًا على خادم داخلي تجريبي.
- قاعدة البيانات المسماة في أمثلة الاتصال هي `ICV_Internal_Staging` وليست قاعدة الإنتاج.
- لا يحتوي المستودع على كلمات مرور أو مفاتيح اتصال حقيقية.

## ما أُضيف في هذه الدفعة

- مشروع ASP.NET Core Web API يستهدف .NET 8.
- اتصال SQL Server عبر إعداد محمي خارج ملفات المصدر.
- ASP.NET Core Identity مع Cookie جلسة HttpOnly وSecure ومدة ساعتين.
- حماية CSRF للطلبات غير الآمنة عبر `X-CSRF-TOKEN`.
- نقطة فحص صحة `GET /api/health`.
- سياق Identity منفصل ومسمّى الجداول بوضوح.

## إعداد محلي تجريبي

1. تثبيت .NET 8 SDK وSQL Server Developer/Express على جهاز الاختبار.
2. إنشاء قاعدة منفصلة باسم `ICV_Internal_Staging`.
3. ضبط متغير البيئة `ConnectionStrings__IcvSqlServer` على اتصال قاعدة الاختبار.
4. من مجلد `backend/Icv.Api` نفّذ:
   ```powershell
   dotnet restore
   dotnet build
   dotnet ef migrations add InitialIdentity --output-dir Data/Migrations
   dotnet ef database update
   dotnet run
   ```
5. تحقق من `/api/health` على عنوان الخدمة المحلي.

## حدود هذه الدفعة — لا تعتبر تحويلًا مكتملًا

- لم تُنفّذ بعد كيانات وواجهات CRUD لجداول المشاريع والتقارير والخطط والجهات والشركات والإعدادات والتدقيق والمتابعة والإشعارات.
- لم تُحوّل صفحات الواجهة من استدعاءات Supabase إلى API.
- لم تُنقل بيانات Supabase أو ملفات Storage.
- يلزم ربط المستخدمين بأدوار المنصة الخمسة وملف `user_profiles`، وفرض انتهاء `temporary_viewer` على الخادم.
- يلزم تنفيذ تحقق الصلاحيات على جميع الجهات: `admin`, `section_head`, `editor` تعديل؛ `viewer`, `temporary_viewer` قراءة فقط.
- يلزم إضافة حماية CSRF token issuance/validation integration في الواجهة قبل اختبار طلبات Cookie.
- لا تستخدم `EnsureCreated` أو ترحيلات هذا المشروع على أي قاعدة إنتاج.

## قاعدة عدم التأثير على المنصة الحالية

لا يتم تحويل أي مستخدم أو تغيير DNS أو تعديل GitHub Pages أو Supabase. جميع التجارب على فرع منفصل وخادم وقاعدة اختبار منفصلين. الانتقال لا يحدث إلا بعد موافقة صريحة واختبارات قبول ونسخة احتياطية وخطة رجوع.

## ربط الواجهة — مرحلة تجريبية جزئية

- أضيف `public/icv-api.js` كعميل داخلي، وحُمّل في `index.html` و`report-form.html`.
- في `ptlc-project-pages.js` أصبحت قراءة سجل المشروع وقائمة تقاريره تستخدم العميل الداخلي عند تفعيل `window.ICV_INTERNAL_API_ENABLED = true`.
- هذا المفتاح **غير مفعّل افتراضيًا**؛ لذلك لا يتغير سلوك الواجهة الحالية عند فتحها على الاستضافة القائمة.
- لا تزال بيانات الجهات والشركات والخطط وملاحظات المشروع وملفات المرفقات وبعض وظائف النموذج تعتمد على Supabase. كما أن صفحة إدخال التقرير لم تُحوّل بعد إلى حفظ API؛ تحميل العميل فيها تجهيز فقط.
- لا تفعّل المفتاح قبل نشر API على نفس الأصل أو إعداد Proxy موثوق، وإكمال تسجيل الدخول الداخلي وملف المستخدم والصلاحيات، ونقل نقاط القراءة المساندة. وإلا ستظهر طلبات غير مكتملة.
- عند تفعيل الربط لاحقًا يجب أن تكون الواجهة مستضافة على خادم الاختبار الداخلي، وليس GitHub Pages.

## واجهات المشاريع والتقارير المنفذة

- `GET /api/projects` مع البحث والحالة والجهة وترقيم الصفحات.
- `GET /api/projects/{id}`
- `POST /api/projects`
- `PUT /api/projects/{id}`
- `GET /api/projects/{id}/reports`
- `POST /api/projects/{id}/reports`
- `POST /api/reports/{id}/submit`
- `POST /api/reports/{id}/approve`

هذه الواجهات أولية وتحتاج اختبارات بناء وتكامل ومراجعة أمنية قبل تشغيلها على خادم الهيئة.


## الدفعة التالية: واجهات مساحة العمل والتخزين الداخلي

أضيفت في هذا الفرع:
- واجهات الجهات الحكومية والشركات: قراءة وإضافة وتعديل، مع إظهار بيانات نقاط الاتصال للموظفين المخولين فقط.
- واجهات خطط المحتوى المحلي: قراءة خطط المشروع وإضافة خطة وتعديلها.
- واجهات ملاحظات/متابعات المشروع: قراءة وإضافة وتعديل، مع الأولوية والحالة وتاريخ الاستحقاق.
- واجهة تعديل التقرير مع منع تعديل التقرير المعتمد.
- واجهة رفع وتنزيل مرفقات التقارير من مجلد خاص خارج wwwroot، مع حد رفع 20 MB والتحقق من مسار الملف عند التنزيل.
- عميل واجهة موسع `icv-api-workspace.js` يوفّر استدعاءات الجهات والشركات والخطط والملاحظات والتقارير والملفات.

إعداد مسار التخزين:
`FileStorage:RootPath`، وإذا لم يُضبط يستخدم `App_Data/PrivateFiles` داخل مجلد التطبيق. يجب ضبطه في بيئة الإنتاج إلى مجلد NTFS خاص بصلاحيات حساب IIS فقط، مع نسخ احتياطي وفحص ملفات ضارة وسياسة احتفاظ.

## حدود مهمة قبل تفعيل التحويل

- هذه الدفعة أضافت نقاط API وعميلها، لكنها لم تستبدل كل استدعاءات Supabase في صفحات الجهات والشركات والخطط والملاحظات.
- صفحة إدخال التقرير لا تزال تحتاج إكمال ربط الحفظ والتعديل والرفع/التنزيل في الواجهة والتحقق من حالات التقرير العربية الحالية. لا تفعّل `ICV_INTERNAL_API_ENABLED` الآن.
- تسجيل الدخول الداخلي موجود في API ويطبّق التحقق من حالة المستخدم وصلاحيته، لكن واجهة الدخول الرئيسية لا تزال تعتمد على Supabase session وتهيئة `boot(session)`. لم يتم استبدالها بعد لأن بقية تهيئة التطبيق وملف المستخدم والتحميل الأولي تعتمد على جلسة Supabase؛ التبديل المباشر سيعطّل التطبيق.
- لم تنفذ عملية إنشاء حسابات Identity وربطها تلقائيًا مع `user_profiles` أو إدارة الأدوار. يلزم endpoint provisioning إداري آمن قبل اختبار دورة المستخدم كاملة.
- لا توجد حتى الآن اختبارات build أو integration أو اختبار ملفات على IIS؛ لذلك لا تعتبر هذه الدفعة جاهزة للإنتاج أو للاستخدام اليومي.

لا تضع مفاتيح Supabase أو بيانات دخول في المستودع. استمر بالعمل على قاعدة اختبار منفصلة فقط.
